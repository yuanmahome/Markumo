### 2.2 基线实测锁定的核心内存增长来源

1. **分离（Detached）DOM 整树驻留泄漏（最严重瓶颈）**：
   - 基线中 `L-open-switch-close-20` 关闭全部文档后连接态 DOM 仅 `180` 个，但引擎总 DOM 节点高达 **`149,889`**，JS 事件监听器累积至 **`5,461`**，WebView2 Private 升至 **`688.70 MiB`**（采样峰值 **`840.24 MiB`**），且在场景 M 等待回收后仍滞留在 `687.39 MiB`。
   - 通过 V8/Blink Heap Snapshot 最短 GC 根持有链定位确认：`images.ts` 销毁时仅调用了 `image.removeAttribute('src')` 而未调用 `image.remove()` 断离父节点；WebView2 (`155.0.4283.62`) 的 `HTMLDocument -> blink::MediaQueryMatcher -> HTMLImageElement::ViewportChangeListener` 强引用了该 `<img>`，进而沿 `parentNode` 链将已销毁文档的整棵 ProseMirror / SplitPreview DOM 子树（含数千节点、KaTeX `MathMLElement` 与闭包监听器）锁死在内存中。
2. **静止浏览时常驻嵌入 CodeMirror 实例及全局监听器膨胀**：
   - 50/100/200 代码块在用户完全未编辑时，仅因落入 `±600px` 观察范围即创建并常驻 `4` 个完整 `CMView`（20 次开闭累计创建 `80` 个）。
   - 同时每个 `CodeBlockView` 无条件创建的 `LanguageSelector` 在构造函数向全局 `document` / `window` 挂载了 `mousedown`、捕获态 `scroll`、`resize` 三个监听器，200 个代码块静止即空耗 `600` 个全局滚动/鼠标监听器（总监听器达 `3,761`）。
3. **Split 双栏重绘风暴与后台无界并发渲染**：
   - `E-md-split`（40 个含 4 种语言的代码块 + 80 个公式 + 4 个 Mermaid）在异步加载 4 种语言时触发了 4 次 `revision.value++` 全文重绘，累计同步执行了 **`200` 次** `syntaxSpans` 解析并并发投递 **`252` 个** 公式/图表任务，产生 `4` 个主线程长任务（共 `258ms`），就绪耗时 `586.9ms`，WebView2 Private 峰值达 `399.93 MiB`。
4. **图片预加载、原图预览接线缺失与缓存残留**：
   - `mountMarkdownImage` 构造时无条件立即调用 `load()` 导致文档内大量离屏图片全部提前加载；`createMarkdownResources` 的 `pending` Map 在请求完成后未删除 Promise，导致 `Uint8Array` 在 JS Heap 留存副本；`MarkdownEditorController` 的“放大预览”遗漏了 `{ full: true }` 原图加载器，且 `ImagePreview` 在异步原图返回前关窗会泄漏孤儿 Blob URL。

|---:|---|---:|---:|

## 5. 高亮与渲染任务队列并发、取消与缓存预算

1. **有界任务队列 (`src/editor/markdown/renderTaskQueue.ts`)**：
   - 代码块展示态高亮队列与 Split 预览代码高亮队列均限制 `concurrency = 2`、`maxQueued = 128`，支持 `'high' | 'normal'` 优先级调度。
   - 排队任务绑定 `AbortSignal`：元素滚出视口、文档切换、Split 关闭或窗口隐藏时，尚未启动的排队任务立即从队列移除并置空闭包引用 `taskRef = null`，防止持有过期 DOM 与文档对象；超出 `maxQueued` 上限时自动淘汰最早普通排队项，杜绝快速滚动无限积压 Promise。
2. **Split 双栏渲染治理 (`rendering.ts` + `splitPreview.vue`)**：
   - 消除了异步语言加载通过 `revision.value++` 引发的整篇文档 5 次重复 `md.parse` + `DOMPurify` 重绘：在 `E-md-split` 中，`syntaxSpans` 执行次数从 **`200` 次降至 `2` 次**，并发渲染任务峰值从 **`252` 降至 `4`**，长任务总时长从 `258ms`（4 个）降至 `72ms`（1 个），场景就绪耗时从 **`586.9ms` 降至 `249.7ms`**。
3. **窗口隐藏暂停与恢复 (`src/editor/markdown/renderVisibility.ts`)**：
   - 统一结合真实滚动容器 `IntersectionObserver` 与 `document.hidden` (`visibilitychange`)：窗口隐藏时暂停非必要的代码高亮、公式编译、Mermaid 渲染及 Split 后台重绘；恢复前台可见时自动按视口恢复脏块增强。
4. **Mermaid 队列取消隔离与双维度缓存预算 (`src/editor/markdown/wysiwyg/renderers.ts`)**：
   - Mermaid 使用 `concurrency = 1, maxQueued = 48` 的可取消队列替代无上限串行链；取消某一个 Pane 的排队请求只移除该调用方条目，绝不破坏另一 Pane 正在等待或已挂载的同源图表结果。
   - 保持原有安全净化（DOMPurify 严格白名单）、SVG ID 与 CSSOM 选择器每次挂载独立命名空间隔离，以及 **公式最多 300 项、Mermaid 最多 30 项** 上限不扩增，新增 UTF-16 估算字节上限（公式 **`2 MiB`**、Mermaid **`4 MiB`**）构成双维度 LRU 淘汰；因挂载均克隆独立 DOM，淘汰缓存字符串不影响任何活动视图已渲染内容。

## 9. 与 Nomo 的架构差异

| 维度 | Nomo 参考实现 | Markumo Phase 04.2 实现 | 差异原因 |
|---|---|---|---|
| 代码块编辑控件 | 展示态 `<pre>`；编辑态切换为 `<textarea>` + 底层同步滚动高亮层，按 `Esc` 取消或 `blur` 提交 | 展示态为 `<pre class="md-code-placeholder">` + Lezer 静态高亮；进入编辑态按需挂载完整 **CodeMirror 6 `EditorView`**，实时同步至外层文档并在安全条件下离开即销毁 | 完整保留 Markumo 原有的多光标/括号匹配、平滑光标、精确 Tab 缩进配置、语言模式、原生 IME 与无损实时双向映射，不退化为普通 `textarea` |
| 语法高亮引擎与预算 | Shiki 异步分词，`DISPLAY_HIGHLIGHT_MAX_CHARS = 80,000` | 复用已有 `@lezer/highlight` + `syntaxSpans`（零新增语法高亮包体积），经本机 Release 实测收紧为 `50,000` 字符 | 避免同时维护 Shiki 与 CodeMirror 两套语法高亮引擎，且 `50,000` 字符实测保证主线程 `0` 长任务 |
| 视口可见性观察 | `IntersectionObserver({ rootMargin: '400px' })`（默认文档视口 root）+ `visibilitychange` | 显式绑定真实 Pane 滚动容器（`.markdown-live` / `.split-preview-content`）作为 `root`，`rootMargin: '400px 0px 400px 0px'` + `visibilitychange` + 离屏高亮数上限 `12` | Markumo 支持任意多 Pane 分栏独立滚动，必须以各 Pane 容器为独立观察 `root` |
| 文档运行时状态 | `MarkdownDocumentRuntime` 绑定标签与编辑器核心，按可见性挂载宿主 | `DocumentManager` 以单一不可变 CodeMirror `EditorState` 作为全文权威状态与统一历史栈，Live 的 ProseMirror 通过 `MarkdownSourceBridge` 增量桥接 | 保持 Markumo 跨 Live / Source / Split 无缝共享同一 Undo/Redo 历史、脏标记与崩溃恢复快照的既有架构 |
| 大文件分段模式 | `SegmentedTextEditorCore` + `virtualScroll`（Rust 持全文，前端持 `512 KiB` 窗口与 `8 MiB` 缓存） | 本轮延期未引入（普通与数 MB 文本继续走轻量直开路径） | 当前 Release 三轮实测证明 `2.5 MiB` 纯文本打开耗时仅 `155~226ms`、增量 Heap 仅约 `8 MiB`，并非当前内存瓶颈 |

## 11. 已知限制

1. **不宣称绝对零泄漏**：V8 JIT 代码缓存、WebView2 浏览器子进程页面池以及 Mermaid 首次动态加载后在引擎内部建立的全局样式/单例结构（约保留固定 `~8,000` 个引擎内部节点但后续 20 轮循环保持恒定不增长）使关闭文档后的内存回落不会回到冷启动的 `185 MiB` 初始值。
2. **离散采样下界**：`250ms` ~ `350ms` 间隔采样的 JS Heap 与进程 Private Bytes 峰值是离散观测下界，不能捕获两次采样之间生命周期极短的瞬时分配尖峰。
3. **超大单代码块与超多图表上限**：单个代码块超过 `50,000` 字符时展示态降级为纯文本（点击编辑仍由 CodeMirror 按视口增量高亮）；Split 预览单次仍保留最多 `16` 个 Mermaid 图表、`256` 个公式、`64` 张图片的既有安全预算。

## 12. 后续是否需要实施大文件分段模式（Phase 5 评估结论）

**结论：本轮明确延期，当前无需实施 `SegmentedTextEditorCore` 大文件分段模式。**

- **实测依据**：在 Windows WebView2 Release 三轮基线与复测（场景 `X-large-txt-2mb`，22,000 行约 2.5 MiB UTF-8 日志文本打开、编辑与撤销）中，主 CodeMirror 6 打开就绪耗时仅 `155ms ~ 226ms`，JS Heap 稳定增量仅约 `8.4 MiB`（`16.43 → 24.84 MiB`），关闭后立即回落至 `16.55 MiB`，WebView2 Private 无异常滞留。
- **工程权衡**：分段文本编辑器需要引入独立的 Rust 会话状态机、全局字节偏移到窗口坐标映射、跨窗口查找替换、独立分段撤销栈及外部冲突协调，复杂度极高。
- **后续触发条件建议**：仅当未来产品明确需要支持 **`>= 32 MiB ~ 100 MiB+` 超大日志 / JSON 文件流畅编辑**（超出当前前端单 `EditorState` 合理内存预算）时，再为超大纯文本/JSON 单独启用参考 Nomo `512 KiB` 窗口 / `8 MiB` 缓存的分段只读或分段编辑通道，且届时仍应保持常规中小型文件的现有快速直开路径不变。
